## 1. 文档目的

本文档记录统一安全 SDK 的初版技术设计和当前已讨论的技术细节，为后续评审、原型验证和实施计划提供设计基线。

本文档当前不代表已批准实施，不创建 GitHub/GitLab 仓库，不发布 Composer 包，不修改现有业务系统。托管位置、仓库可见性和正式发布渠道尚未最终确定。

## 2. 背景、现状与约束

当前存在多个相互独立的 Laravel/PHP/MySQL 系统。系统之间存在内部接口调用，同时部分接口需要向外部合作方开放。每次增加新的调用关系，通常需要在调用方和被调用方分别新增或修改：

- 请求鉴权、签名与验签；
- 请求或响应数据加密、解密；
- Token 签发与验证；
- 不同系统、合作方的密钥和算法配置；
- 中间件、HTTP 客户端、异常、日志和测试代码。

现有实现分散在多个 Middleware、Service、Controller 和辅助函数中，存在 AES、HMAC、JWT 等多种独立实现。部分逻辑重复，协议和密钥来源不统一。新增接入时需要在多个仓库之间复制、修改代码，容易发生算法参数、签名原文、编码方式不一致，以及密钥误用、日志泄密和安全修复遗漏。

当前约束：

- 暂时不能统一部署内部 API 网关；
- 各系统独立部署，短期内不适合建设集中式鉴权或密钥管理平台；
- 主要技术栈相近，均以 Laravel/PHP 为主；
- SDK 最低 Laravel 约束为 `>=8.5`；
- SDK 最低 PHP 约束为 `>=7.4`；
- 本次设计不使用 MySQL，也不为 SDK 声明 MySQL 版本要求；需要状态存储的能力只依赖抽象接口和部署方选择的实现；
- 可以通过 Composer/Laravel 扩展包统一公共安全能力；
- SDK 未来既要支持内部系统，也要支持外部合作方；
- 认证、签名、加解密、Token 等方式必须可配置，不能写死；
- 当前 SDK 先保存在本地目录，正式托管和发布位置以后确定。

## 3. 建设目标

建设一个单一 Composer 包，对外提供一致接口，对内按模块组织多种安全能力：

1. 统一内部系统和外部合作方的调用身份模型；
2. 统一认证、签名、验签、防重放和权限校验；
3. 统一请求与响应的加密、解密和协议封装；
4. 提供可选的授权 Token 签发、解析和验证能力；Refresh Token 另行设计；
5. 支持按系统、合作方或调用关系选择不同策略和密钥；
6. 新增算法只扩展 SDK 策略，不修改业务调用主流程；
7. 安全修复通过 SDK 新版本分发，各系统按计划升级；
8. 支持旧协议渐进迁移，不要求一次性改完所有系统；
9. 为未来接入 Vault、KMS、统一身份中心或 API 网关保留接口。
10. 在 Laravel/PHP 参考实现成熟后，以同一协议规范扩展 Python、Go、Java、Android、HarmonyOS 和 iOS SDK。

## 4. 非目标与安全边界

首阶段不做：

- 不建设统一 API 网关、流量转发服务或完整 OAuth 2.0/OIDC 平台；
- 不建设集中式管理后台；
- 不把生产密钥保存在 SDK、Git 仓库或 Composer 包中；
- 不让每个安装 SDK 的系统默认拥有 Token 签发权；
- 不允许外部请求自行决定服务端认证、签名或加密算法；
- 不替代 TLS，生产接口仍必须使用 HTTPS；
- 不把资源所有权、租户隔离等业务权限全部塞进 SDK。

## 5. 方案比较

### 5.1 各项目独立实现

短期改动小，但重复代码、协议漂移和安全修复遗漏会持续存在，不能解决核心问题，不采用。

### 5.2 统一网关、认证中心和集中式密钥平台

长期治理能力最强，但当前基础设施和迁移成本不允许。保留为长期演进方向。

### 5.3 统一 Composer/Laravel 安全 SDK

利用现有技术栈，将安全协议、策略接口、Laravel 中间件和 HTTP 客户端封装为版本化软件包。每个系统仍独立部署，通过配置选择身份、算法和密钥。该方案不能提供网关级集中治理，但最符合当前条件，作为推荐方案。

## 6. 总体架构与包身份

```text
业务 Controller / Service / Job
              │
              ▼
       SDK 统一门面与接口
              │
     ┌────────┼─────────┐
     ▼        ▼         ▼
 认证策略   加密策略   Token 策略
     │        │         │
     └────────┼─────────┘
              ▼
       Profile 配置解析
              │
              ▼
         KeyProvider
              │
       ┌──────┴──────┐
       ▼             ▼
  环境变量/文件    未来 Vault/KMS
```

建议稳定身份：

```text
中文名称：Tozo 统一身份认证与安全通信 SDK
Composer 包名：tozo/security-sdk
PHP 命名空间：Tozo\Security
Laravel 配置名：tozo_security
环境变量前缀：TOZO_SECURITY_
```

正式仓库位置改变时，原则上保持 Composer 包名和 PHP 命名空间不变；这只能降低包来源迁移成本，不能替代协议、配置和密钥兼容性验证。

建议单包内部模块：

```text
src/
├── Authentication/     API 认证策略与认证结果
├── Signature/          签名、验签、规范化和防重放
├── Encryption/         请求/响应加解密和信封协议
├── Identity/           service、partner、user 身份模型
├── Token/              Token 签发、解析、验证和刷新
├── Scope/              Scope 定义、匹配和授权
├── Key/                密钥提供器、版本和轮换
├── Protocol/           协议版本、请求上下文和序列化
├── Http/               自动签名/加密的调用端 Client
├── Laravel/            ServiceProvider、Middleware、Facade
├── Audit/              安全日志、脱敏和关联 ID
├── Contracts/          对外稳定接口
└── Exceptions/         统一异常体系
```

首阶段发布为一个 Composer 包，避免多个包的版本兼容和安装复杂度；内部保持清晰边界，未来确有需要时再拆包。首版 Provider 先采用一个根 Provider 加配置驱动的功能注册，只有模块依赖明显复杂时才拆分多个功能 Provider。

PHP/Laravel 是首个参考实现，不是线上协议本身。通信协议不得依赖 PHP 数组、PHP 对象序列化、Laravel Helper 或框架内部行为。未来所有语言实现都以语言无关协议规范和一致性测试向量为准，不以某个 SDK 的内部源码为准。

## 6.1 运行环境和依赖基线

首版 SDK 的运行环境最低基线如下：

```json
{
  "require": {
    "php": ">=7.4",
    "illuminate/support": "^8.5"
  }
}
```

如果 SDK 以完整 Laravel 框架集成包形式发布，则应用仍必须满足 Laravel `>=8.5`；首个正式发布包应只声明已验证的 Laravel `^8.5`。后续 Laravel 主版本必须在 CI 验证通过后，才逐一加入 Composer 约束，例如：

```json
{
  "require": {
    "php": ">=7.4",
    "laravel/framework": "^8.5"
  }
}
```

说明：

- PHP 最低版本语义固定为 `>=7.4`；PHP 7.4 只是兼容基线，生产部署优先选择仍受官方安全维护的 PHP 版本；
- Laravel 最低版本语义固定为 `>=8.5`；“最低版本”不等于“所有更高主版本已经兼容”；
- Composer 发布约束必须只包含已通过 CI 的 Illuminate/Laravel 主版本。首版从 `^8.5` 开始；未通过测试的新主版本不得仅依据 `>=` 宣称兼容；
- PHP 7.4 与各 Laravel 主版本的组合必须在兼容矩阵中逐项列出，不得把不可能的版本组合写成单一范围；
- 若某个主版本尚未验证，后续发布版本应通过扩展约束或冲突约束明确边界，而不是依赖 Composer 的宽松解析。

### 存储依赖边界

SDK 核心和首版设计不使用 MySQL，也不声明任何 MySQL 版本要求。核心安全能力包括：

- 请求签名与验签；
- AES/Sodium 加解密；
- JWT Token 签发与验证；
- Scope 解析与内存内授权判断；
- 环境变量、受控文件和外部 KeyProvider；
- 通过 `ReplayStoreInterface` 提供共享防重放状态；
- 通过 `TokenRevocationStoreInterface` 提供 Token 吊销状态；
- 通过 `AuditSinkInterface` 提供可选审计输出。

这些状态存储只依赖接口，不绑定 MySQL、某个 ORM 或某种数据库表。首版可提供 Laravel Cache/Redis 适配器；其他存储实现必须满足相同的原子性、TTL 和故障处理契约。SDK 不因为安装核心包而创建业务表、执行数据库迁移或强制连接数据库。

## 7. 可配置策略模型

SDK 使用三层机制：

1. **策略实现层**：SDK 提供具体算法实现；
2. **Profile 配置层**：应用为每个调用对象选择策略和参数；
3. **密钥提供层**：KeyProvider 根据 `key_id` 和版本读取真实密钥。

稳定接口建议包括：

```text
AuthenticatorInterface
SignerInterface
PayloadCipherInterface
TokenIssuerInterface
TokenVerifierInterface
KeyProviderInterface
ScopeAuthorizerInterface
ReplayStoreInterface
TokenRevocationStoreInterface
ResponseIntegrityInterface
ClockInterface
```

允许配置：

- 认证、请求签名、请求/响应加密和 Token driver；
- Token issuer、audience、TTL 和允许 Scope；
- 时间戳有效窗口、时钟偏差、Nonce 和防重放 TTL；
- 协议版本、编码方式、Header 名称；
- 按用途区分的 key ID、当前密钥版本和兼容验证版本；
- 是否加密请求/响应、主体类型及允许访问范围。

禁止配置或动态行为：

- 请求不能传入任意算法类名或未注册 driver；
- 不能仅根据 JWT Header 的 `alg` 自动信任和切换算法；
- 禁止 `alg=none`；
- 请求方不能改变 Profile、Audience、Scope、Token TTL 或验证策略；
- 生产环境不能静默降级到弱算法、默认密钥或明文模式。

所有 driver 必须白名单注册。应用启动或首次使用时校验配置，非法配置直接失败。

## 8. Profile 设计

Profile 表示一组明确且单向的通信信任关系，而不是单纯表示一个系统。Profile 必须声明 `direction=inbound` 或 `direction=outbound`，不能在同一个配置块中混用接收方验证规则和发起方出站规则。每个内部系统、外部合作方或调用方向目标服务的关系使用独立 Profile；同一个系统可以拥有多个 Profile，分别绑定不同的目标服务、Audience、Scope、协议版本和用途密钥。

```php
return [
    'default_profile' => env('TOZO_SECURITY_DEFAULT_PROFILE'),

    'features' => [
        'authentication' => true,
        'signature' => true,
        'encryption' => true,
        'response_integrity' => true,
        'token_verifier' => true,
        'token_issuer' => false,
        'token_revocation' => false,
        'scope' => true,
        'http_client' => true,
        'audit' => true,
    ],

    'profiles' => [
        'product_center_to_order_api' => [
            'enabled' => true,
            'direction' => 'outbound',
            'client_id' => 'product-center-production',
            'subject_type' => 'service',
            'subject_id' => 'product-center',
            'target_service' => 'order-api',
            'security_mode' => 'token_plus_request_signature',

            'authentication' => [
                'driver' => 'jwt',
            ],

            'signature' => [
                'enabled' => true,
                'driver' => 'hmac_sha256',
                'key_id' => env('TOZO_SECURITY_PRODUCT_CENTER_SIGNING_KEY_ID'),
                'max_age_seconds' => 300,
                'clock_skew_seconds' => 60,
                'replay_protection' => true,
                'replay_safety_margin_seconds' => 5,
            ],

            'encryption' => [
                'enabled' => true,
                'driver' => 'aes_256_gcm',
                'key_id' => env('TOZO_SECURITY_PRODUCT_CENTER_ENCRYPTION_KEY_ID'),
                'encoding' => 'base64url',
            ],

            'response_integrity' => [
                'required' => true,
                'mode' => 'encrypted',
                'encryption' => [
                    'driver' => 'aes_256_gcm',
                    'key_id' => env('TOZO_SECURITY_ORDER_API_RESPONSE_ENCRYPTION_KEY_ID'),
                ],
            ],

            'token' => [
                'attach_enabled' => true,
                'verify_enabled' => false,
                'issue_enabled' => false,
                'driver' => 'jwt_rs256',
                'issuer' => 'tozo-auth',
                'audience' => ['order-api'],
                'ttl_seconds' => 900,
                'allowed_subject_types' => ['service'],
                'allowed_scopes' => [
                    'product.read',
                    'product.write',
                ],
                'revocation' => [
                    'enabled' => false,
                ],
            ],
        ],
    ],
];
```

此处是出站 Profile 配置结构提案，供后续协议评审冻结。示例中的 `security_mode` 明确要求身份认证和请求完整性同时通过，不得把两者实现成“验签或验证 Token”的模糊 OR 逻辑。`response_integrity.mode` 在首版只能为 `encrypted` 或 `signed`：前者必须配置 `response_integrity.encryption`，后者必须配置 `response_integrity.signature`；禁止用 `encrypted_or_signed` 让同一个 Profile 在运行时接受两种未固定的响应保护方式。响应加密密钥和响应签名密钥均属于独立用途，不能复用请求加密或请求签名密钥。入站 Profile 应将 `token.verify_enabled=true`，并显式配置 `expected_client_id`、允许 issuer/audience、允许 `kid` 和服务端验证公钥来源。`token.issue_enabled` 只允许出现在指定的签发方 Profile。敏感密钥不能直接写入配置数组。

### 8.1 Profile 与功能模块的关系

Profile 和功能模块注册解决的是两个不同层面的问题：

- **Profile**：定义某个单向通信信任关系使用什么本地或预期对端身份、目标服务、认证方式、请求完整性、加密算法、Token 参数、Scope 和用途密钥；
- **功能模块注册**：定义当前 Laravel 应用实际启用哪些 SDK 能力，以及哪些接口可以注入到容器中。

每个内部系统、每个外部合作方和每个高风险调用关系必须使用独立 Profile。对同一条调用链，调用方使用一个 `outbound` Profile，被调用方使用一个 `inbound` Profile；两者由 Protocol v1 的 client、Audience、协议版本和用途 key ID 关联，而不是共享同一配置文件。不同 Profile 可以选择不同 driver 和密钥，但不能因为共用一个 SDK 包就共用默认密钥或隐式继承另一方的权限。

建议在应用配置中显式声明功能：

```php
'features' => [
    'authentication' => true,
    'signature' => true,
    'encryption' => false,
    'response_integrity' => true,
    'token_verifier' => true,
    'token_issuer' => false,
    'token_revocation' => false,
    'scope' => true,
    'http_client' => true,
    'audit' => true,
],
```

有效能力必须同时满足两个条件：

```text
应用功能已启用
    AND
Profile 中实际引用了该功能且配置合法
```

例如应用只验证外部 JWT，不负责签发 Token 时，应启用 `token_verifier`，关闭 `token_issuer`，不要求部署 JWT 私钥。若 Profile 引用了已关闭的 `encryption`、`response_integrity`、`token_issuer` 或 `token_revocation`，结构校验阶段应直接抛出配置异常，而不是运行到请求时才出现容器解析错误。

配置校验分为两个阶段：

1. **结构校验**：在 `config:cache`、应用启动或 `tozo:security:check-config` 中检查字段结构、功能开关、Profile 引用、driver 白名单、静态值格式和接口依赖关系；不读取生产密钥，不连接 Redis，不把构建环境当成生产环境。
2. **运行时校验**：首次解析具体功能时由 KeyProvider 读取真实密钥，由 ReplayStore/TokenRevocationStore 检查外部依赖和原子能力；读取失败或依赖不可用必须抛出明确异常并按安全失败规则拒绝请求。

### 8.2 配置优先级与默认值

未填写的可选参数应按以下优先级解析：

```text
Profile 显式值
  > 应用级 tozo_security.defaults
  > SDK 内置安全默认值
  > 对安全必填项直接失败
```

建议配置合并规则：

- 缺少字段：使用下一层默认值；
- 显式 `null`：安全字段一律视为配置错误；行为字段只有文档明确允许时才能为 `null`，不能把 `null` 当作关闭或无限制；需要关闭功能时使用明确的 `enabled=false`；
- 空字符串、非法数字、非法 driver：视为配置错误，不回退默认值；
- 数组型配置采用显式替换或明确的深度合并规则，不能依赖 PHP 数组运算符产生隐式结果；
- 配置缓存后，运行时不再从请求参数覆盖配置。

### 8.3 建议默认值

以下默认值只用于行为参数，不包含任何真实密钥：

| 参数 | 默认值 | 说明 |
|---|---:|---|
| `protocol.version` | `1` | 未指定协议版本时使用当前 SDK 基线版本 |
| `encoding` | `base64url` | Token、签名和信封的默认编码 |
| `signature.driver` | `hmac_sha256` | 仅在 Profile 明确启用签名且未指定 driver 时使用 |
| `signature.max_age_seconds` | `300` | 签名最大年龄 |
| `signature.clock_skew_seconds` | `60` | 调用双方允许的时钟偏差 |
| `signature.replay_protection` | `true` | 默认开启防重放 |
| `signature.replay_safety_margin_seconds` | `5` | ReplayStore TTL 的最小额外安全余量 |
| `encryption.driver` | `aes_256_gcm` | 仅在 Profile 明确启用加密且未指定 driver 时使用 |
| `token.ttl_seconds` | `900` | Access Token 默认有效期 |
| `token.clock_skew_seconds` | `60` | Token 时间校验偏差 |
| `scope.denied_by_default` | `true` | 未声明 Scope 时默认拒绝 |
| 可选功能 `enabled` | `false` | 未显式启用的功能不注册容器绑定 |

认证 driver、签名 driver、加密 driver 和 Token driver 只有在 Profile 已明确启用对应功能时才允许使用 SDK 默认值；外部合作方 Profile 必须显式指定 driver、协议版本、用途 key ID 和身份参数，避免双方各自理解不同的默认协议。

### 8.4 必须显式配置的参数

以下参数缺失时必须失败，不能回退到全局默认值、其他 Profile 或随机尝试的密钥：

- 签名或 HMAC 所需的 `key_id` 和真实密钥；
- AES-GCM/Sodium 所需的加密密钥和 `key_id`；
- 出站 Token 附加所需的受控 Token 来源、`issuer`、`audience` 和允许 Scope；
- JWT-RS256 签发所需的私钥、`issuer`、`audience` 和 `signing_key_id`；
- 入站 JWT 验证所需的公钥来源、允许的 `issuer`、`audience` 和允许的 `kid` 集合；
- 启用响应完整性所需的固定 `mode`，以及对应的响应加密或响应签名 driver、`key_id` 和真实密钥；
- 外部合作方的 `client_id`、身份类型和允许 Scope；
- 启用防重放时的共享 `ReplayStore` 实现；
- 启用 Token 吊销时的独立 `TokenRevocationStore` 实现；
- `security_mode` 与 `authentication`、`signature`、`response_integrity` 的一致配置。

这样既能减少重复配置，又不会因为“自动默认”导致多个系统错误共用密钥或把 Token 发送给错误的受众。

## 9. 身份主体模型

首阶段支持：

| 类型 | 含义 | `sub` 示例 | 场景 |
|---|---|---|---|
| `service` | 内部系统或后台服务 | `service:product-center` | Laravel 系统间调用 |
| `partner` | 外部合作方应用 | `partner:aichat` | 合作方服务器调用内部接口 |
| `user` | APP/Web 登录用户 | `user:380354` | 跨系统传递用户身份 |

后续按需求扩展 `device`、`job` 和代理主体。主体、客户端和租户必须区分：

- `sub`：Token 代表的主体，首版按 `subject_type:subject_id` 生成并校验；
- `client_id`/`azp`：取得并使用 Token 的应用；
- `tenant_id`：所属租户上下文，不替代主体；
- `act`：服务代表用户操作时的代理主体。

密码学验证得到的 `client_id`、`azp`、`sub`、`iss`、`aud` 或 HMAC `key_id` 归属必须与已解析的 Profile 完全匹配。Header 中的客户端或 Profile 标识只能作为查找提示，不能作为最终身份依据。

服务端 Profile 解析顺序固定如下：

```text
1. 路由明确绑定 Profile 时，直接取得该唯一候选；
2. 否则将 Header 中的 client_id、key_id、issuer/audience 仅作为不可信索引，查询服务端 Profile Registry；
3. 候选必须唯一；未知或多个候选均拒绝，禁止遍历 Profile 直到某个验签成功；
4. 使用候选 Profile 的固定算法和白名单完成密码学验证；
5. 把验证得出的主体、客户端、issuer、audience、key 归属与候选 Profile 再次逐项比对；
6. 任一不一致返回 `profile_subject_mismatch`，不得切换到其他 Profile 重试。
```

`default_profile` 仅供调用端在本地明确选择出站配置；服务端不得因为入站请求缺少身份信息而回退到默认 Profile。

## 10. API 认证策略

| Driver | 用途 | 首版建议 |
|---|---|---|
| `hmac_bearer_sha256` | 使用 HMAC 证明持钥方身份 | 支持，必须明确用途密钥 |
| `jwt` | 使用已签发 Token 认证 | 支持，仅提供 Token 级身份和完整性 |
| `api_key` | 简单合作方身份识别 | 仅作为身份提示，必须叠加请求签名、TLS、限流和权限 |
| `legacy_signature` | 兼容现有自定义签名协议 | 仅迁移使用 |

认证、请求完整性、加密和授权含义不同：认证确认身份，请求签名保证当前请求上下文和最终 Body 未被篡改，加密保护报文内容，Scope 决定主体允许做什么。认证成功不代表请求完整性验证成功，Token 验证也不自动绑定 HTTP 方法、路径或 Body。

每个 Profile 必须显式选择一种安全模式，首版支持：

| 模式 | 要求 | 适用边界 |
|---|---|---|
| `token_only` | Token 认证通过，且请求签名关闭 | 仅允许明确标记为 TLS 保护的低风险、幂等接口；不得把它当作写接口的默认模式 |
| `signed_request` | 请求签名通过；签名 `key_id` 的归属是该模式唯一的认证主体 | 内部服务或受控合作方的服务调用 |
| `token_plus_request_signature` | Token 认证 **AND** 请求签名均通过 | 写操作、敏感操作和外部合作方调用的默认推荐模式 |

安全模式与 Profile 开关必须能进行结构校验：`token_only` 要求 `signature.enabled=false` 且入站 `token.verify_enabled=true`/出站 `token.attach_enabled=true`；`signed_request` 要求 `signature.enabled=true`，并禁止把 Token 作为第二个认证分支附加或验证；`token_plus_request_signature` 要求两类功能均开启，入站必须验证 Token 和签名，出站必须附加 Token 和签名。`inbound`/`outbound` 的具体开关分别校验，不能只因另一方向配置正确就通过。

首版不允许使用未定义的“验签或验证 Token”流程。路由策略、Profile 和安全模式共同决定必须满足的条件，不能在一种验证失败后自动尝试另一种算法或身份来源。

## 11. 请求签名、验签与防重放

新接入默认建议 HMAC-SHA256。请求签名绑定最终实际发送的 wire-level Body，规范化内容至少包括：

```text
protocol version
HTTP method
normalized path
normalized query string
content type
body SHA-256 hash
timestamp
nonce
client/subject identifier
audience/target service
key id
```

调用方对最终实际发送的原始 Body 计算哈希。请求加密时采用“先加密、后签名（Encrypt-then-Sign）”：先生成最终信封，再对最终 Body 做哈希并签名；未加密请求直接对原始 Body 签名。这样服务端可以在解密前验证身份和签名，并且只把已通过密码学验证的 Nonce 写入 ReplayStore，避免无效请求污染防重放状态。

Protocol v1 必须冻结以下字节级规则：UTF-8、换行符、字段顺序和分隔符、HTTP method 大小写、path 规范化、query 排序与百分号编码、Content-Type 表示、空 Body 表示、JSON 数字和 Unicode 处理、时间戳单位、Nonce 长度和字符集、Base64URL padding，以及常量时间比较方式。任何语言不得直接使用本语言默认序列化结果。

每个签名请求包含时间戳、高熵随机 Nonce、有限有效窗口、请求上下文、Body Hash、key ID 和协议版本。服务端处理顺序固定为：

```text
解析唯一 Profile 候选
  → 检查协议版本、必要 Header 和时间窗口
  → 验证 Token/认证证明
  → 验证请求签名
  → 校验密码学主体与 Profile 绑定
  → ReplayStore 原子写入 Nonce
  → 解密请求体
  → 校验 Scope
  → 执行业务
```

ReplayStore 必须是所有服务实例可访问的共享、具备原子“只写一次”语义的存储；多实例部署不得使用进程内数组或单机文件作为生产实现。Redis 适配器应使用等价于 `SET key value NX EX ttl` 的原子操作。存储故障、超时、格式异常或原子能力不可确认时必须拒绝请求，不得降级为仅时间校验。

ReplayStore 写入时的 TTL 必须覆盖完整可接受窗口。若 TTL 从收到请求并写入缓存的时刻开始计算，至少满足：

```text
replay_ttl_seconds
  = max_age_seconds
  + (clock_skew_seconds * 2)
  + replay_safety_margin_seconds
```

默认值为 `300 + 2*60 + 5 = 425` 秒；实现不得把 TTL 设置得低于该结果。重复 Nonce 返回 `replay_detected`。

建议 Header：

```text
X-Tozo-Protocol-Version
X-Tozo-Client-Id
X-Tozo-Key-Id
X-Tozo-Timestamp
X-Tozo-Nonce
X-Tozo-Signature
X-Request-Id
Authorization
```

最终 Header 名称和 `X-Tozo-Profile-Id` 是否允许作为查找提示在协议评审时冻结。任何 Header 都不能直接指定 driver、算法、Audience 或密钥；旧系统由适配器转换。

## 12. 请求与响应加解密

| Driver | 用途 | 首版建议 |
|---|---|---|
| `aes_256_gcm` | 新系统对称认证加密 | 默认支持 |
| `sodium_secretbox` | Sodium 对称认证加密 | 可选扩展 |
| `legacy_aes_128_cbc` | 兼容现有系统 | 仅迁移使用 |

新协议优先使用 AEAD 算法，如 AES-256-GCM。AES-CBC 本身不提供完整性校验，不作为新接入默认方案。兼容旧 AES-128-CBC 时必须通过独立 legacy driver 显式启用并补充 MAC，不允许静默回退。

建议使用版本化加密信封：

```json
{
  "version": "1",
  "algorithm": "aes_256_gcm",
  "key_id": "product-center-enc-2026-01",
  "iv": "base64url-value",
  "ciphertext": "base64url-value",
  "tag": "base64url-value"
}
```

`algorithm` 和 `key_id` 只用于描述报文格式和索引候选密钥，服务端仍以 Profile 白名单为准；它们必须与 Profile 的预期 driver 和允许 key ID 一致，不一致立即拒绝，不能忽略字段后继续解密或尝试其他算法。

AES-256-GCM 的 `iv` 是 96-bit nonce。每次加密必须由 SDK 内部以 CSPRNG 自动生成新的 12 字节值；对同一个加密密钥绝不允许重用。业务调用方不能向加密 API 传入、固定、覆盖或复用 `iv`，也不能使用全零或默认 `iv`。解密端只读取并验证信封携带的 `iv`，不提供“自行指定解密 IV”的兼容回退。密钥轮换可以降低长期风险，但不能替代 nonce 唯一性。

AAD 必须绑定协议版本、方向（`request` 或 `response`）、调用方、目标服务、HTTP method、规范化 path 和加密 `key_id`，防止密文被复制到另一方向、另一客户端或另一接口。AAD 的精确字节序列、tag 长度、Base64URL 编码和错误码必须在 Protocol v1 冻结；任何 AAD、tag、nonce 或密文校验失败都返回统一的解密失败结果，不能部分解析明文。

报文加密不替代 HTTPS。是否启用根据 Profile 和数据敏感性决定，不因 SDK 支持加密就默认重复加密全部数据。首版 `response_integrity.mode` 必须固定为 `encrypted` 或 `signed`：`encrypted` 表示响应采用指定的 AEAD 加密，GCM tag 覆盖的密文与 AAD 构成响应完整性证明；`signed` 表示响应不加密，服务端必须在最终响应 Body 上生成方向为 `response` 的应用层签名，客户端验证后才能把数据交给业务。两种模式均拒绝未受保护的响应，且响应签名或响应加密不得与请求共用同一用途密钥。

## 13. Token 设计

| Driver | 用途 | 首版建议 |
|---|---|---|
| `jwt_rs256` | 非对称 JWT，签发方持私钥、验证方持公钥 | 推荐支持 |
| `jwt_hs256` | 共享密钥 JWT | 可配置，不建议多系统广泛使用 |
| `opaque_token` | 随机不可读 Token，依赖查询或内省 | 后续扩展 |

Tozo Token 是本协议定义的 JWT Profile，不自动宣称与完整 OAuth 2.0/OIDC 的授权端点、发现机制或 wire 协议兼容。Token 签发模块必须显式开启。默认安装只允许验证，不允许签发。只有指定系统同时配置私钥、`token.issue_enabled=true`、`features.token_issuer=true`、允许主体类型、允许 Audience 和允许 Scope 后才能使用 `TokenIssuerInterface`。

JWT Header 与 Payload 示例（用于说明字段结构，不是 JWT 紧凑序列化后的原始值）：

```json
{
  "header": {
    "alg": "RS256",
    "typ": "JWT",
    "kid": "tozo-auth-2026-08"
  },
  "payload": {
    "iss": "tozo-auth",
    "sub": "service:product-center",
    "aud": ["order-api"],
    "scope": ["order.read"],
    "client_id": "product-center-production",
    "jti": "唯一Token ID",
    "iat": 1787100000,
    "nbf": 1787100000,
    "exp": 1787100900
  }
}
```

JWT Header 中的 `kid` 必须在验证前映射到 Profile 允许且状态可验证的公钥；不得扫描所有公钥或依赖 Header `alg` 选择算法。验证必须覆盖固定算法、签名、`kid`、issuer、audience、`iat/nbf/exp`、主体格式、`client_id`/`azp`、Scope 和 Profile 身份绑定。

`jti` 是 Token 的唯一标识，用于吊销和审计，不等同于每请求防重放。Bearer Token 在有效期内可被重复提交；需要请求级防篡改和防重放的 Profile 必须选择 `token_plus_request_signature` 或以后定义的 sender-constrained 证明，不能仅依赖 `jti`。

启用吊销时，`TokenRevocationStoreInterface` 与 `ReplayStoreInterface` 是两个独立契约，禁止混用同一条记录语义。吊销记录至少以 `jti` 为键，并在 `exp + token.clock_skew_seconds` 后过期。查询成功且未吊销才允许继续；已吊销、连接故障、超时、数据格式异常或存储不可用均必须拒绝 Token，reason code 分别为 `token_revoked` 或 `revocation_store_unavailable`。首版推荐用具备 TTL 的共享缓存存储吊销记录，不因启用吊销而强制数据库查询。

生命周期原则：

- Access Token 短期有效；
- 内部服务、外部合作方和用户 Token 使用不同客户端与权限；
- 用户 Token 不得当作服务 Token，服务 Token 不得伪装用户；
- Refresh Token 不是首版 Protocol v1 的实现范围；确有用户会话需求时由后续独立设计定义签发、轮换、吊销、保密存储和审计规则；
- SDK 提供通用 Token 验证与受限签发能力，登录流程、凭证审核和授权审批仍属于业务系统或未来身份中心。

## 14. Scope 权限模型

Scope 使用资源与动作形式：

```text
product.read
product.write
traffic.calculate
user.profile.read
```

Profile 必须声明允许的主体类型与 Scope 集合；签发方只能签发以下交集，且不得扩大权限：

```text
granted_scopes
  = requested_scopes
  ∩ profile.allowed_scopes
  ∩ issuer.allowed_scopes
```

接口授权条件为 `required_scopes ⊆ granted_scopes`。验证端还必须确认 `sub` 的类型与 Profile `allowed_subject_types` 相符；用户、服务和合作方 Scope 不得通过名称相同而互相替代。资源所有权、租户隔离和行级权限仍由业务层处理。

首版不支持任意通配符，避免 `*` 或 `product.*` 导致越权。

## 15. 密钥管理和轮换

SDK 不持久化、不托管、不在包内生成生产密钥；只定义 KeyProvider，并在运行期间按需把真实密钥保留于进程内存。首阶段提供：

- `EnvironmentKeyProvider`：读取部署环境变量；
- `FileKeyProvider`：读取权限受控的密钥文件，适合 RSA 密钥；
- `ArrayKeyProvider`：仅测试环境使用。

未来可扩展 Vault、云 KMS 或公司自建密钥平台。

密钥隔离要求：

- 每个系统或合作方独立密钥；
- 请求签名、响应签名、加密和 Token 签发密钥按用途分离；
- 测试、预发布、生产环境分离；
- 内部系统和外部合作方分离；
- JWT 私钥只存在于授权签发方，验证方只持公钥；
- 密钥不得进入日志、异常、Git、Composer 包或普通数据库字段。

Profile 应使用清晰的用途字段，而不使用一个泛化 `key_id`：

```text
signature.key_id
response_integrity.encryption.key_id
response_integrity.signature.key_id
encryption.key_id
token.signing_key_id
JWT Header.kid
```

协议中携带的 `key_id` 或 `kid` 只能索引该用途、该 Profile 白名单内的候选密钥。签发、请求签名和加密只使用当前 `active` 密钥；验签、响应验签、解密和 JWT 公钥验证可在明确迁移期内接受标记为 `verify_only` 或 `decrypt_only` 的旧版本。状态建议：

```text
pending → active → verify_only/decrypt_only → retired
```

HMAC 共享密钥轮换必须有明确的短迁移窗口和双方切换计划；JWT 公钥验证窗口可以与 Access Token 最大寿命及 `clock_skew` 对齐；加密旧密钥的 `decrypt_only` 保留时长由仍需读取的历史密文决定。未知 key ID、已退休密钥或读取失败必须明确报错，不尝试所有密钥，也不回退到默认密钥。

## 16. Laravel 集成和调用流程

SDK 应提供：

- ServiceProvider 和可发布配置；
- 认证、验签、解密、Scope Middleware；
- 自动签名/加密的安全 HTTP Client；
- 可选 Facade，核心代码仍依赖接口；
- Laravel Cache/Redis ReplayStore；
- Laravel Cache/Redis TokenRevocationStore；
- Laravel Log 审计适配器；
- 配置检查、密钥生成和协议自检命令，但不得输出生产私钥。

### 16.1 Laravel 容器按需注册

单包不等于所有功能都必须在每个项目中启用。推荐使用一个根 `TozoSecurityServiceProvider` 负责读取配置、建立策略注册表和校验 Profile，再由功能模块按配置注册各自的绑定：

```text
TozoSecurityServiceProvider（始终加载）
  ├── AuthenticationServiceProvider（features.authentication=true）
  ├── SignatureServiceProvider（features.signature=true）
  ├── EncryptionServiceProvider（features.encryption=true）
  ├── ResponseIntegrityServiceProvider（features.response_integrity=true）
  ├── TokenVerifierServiceProvider（features.token_verifier=true）
  ├── TokenIssuerServiceProvider（features.token_issuer=true）
  ├── TokenRevocationServiceProvider（features.token_revocation=true）
  ├── ScopeServiceProvider（features.scope=true）
  ├── HttpClientServiceProvider（features.http_client=true）
  └── AuditServiceProvider（features.audit=true）
```

Laravel 容器建议遵循以下规则：

1. 根 Provider 可以通过 Composer package discovery 自动加载，也允许宿主项目手动注册；
2. 功能 Provider 只在对应 feature 显式开启且至少一个 Profile 使用该功能时注册；
3. 接口绑定使用 `singleton` 或 `scoped` 时必须依据对象是否持有请求状态决定，默认优先无状态 singleton；
4. 策略实现采用延迟解析，注册阶段不读取全部密钥、不创建全部客户端、不连接 Redis；
5. `KeyProvider`、配置解析器和策略注册表属于共享基础依赖，但真实密钥仅在某个功能第一次被解析时读取；
6. Token 签发和 Token 验证必须分开绑定，关闭 `token_issuer` 时不注册 `TokenIssuerInterface`，避免无意加载私钥；
7. Profile 引用了未启用的功能、未知 driver、无效静态格式或缺失接口绑定时，在应用启动或配置缓存阶段失败，并报告明确错误；生产密钥读取、Redis 连接和其他外部依赖连通性只在运行时校验；
8. 不允许通过请求参数临时触发 Provider 注册或切换容器绑定；
9. `php artisan tozo:security:check-config` 默认只检查“功能开关 → Profile 引用 → driver → key ID 格式 → 接口绑定”的结构链路；显式使用 `--runtime` 时才允许检查受控环境中的 KeyProvider 与状态存储连通性，且不得输出任何密钥；

因此，宿主项目的使用方式应接近：

```php
// 业务代码只注入当前项目实际启用的接口。
public function __construct(SignatureVerifierInterface $verifier)
{
    $this->verifier = $verifier;
}
```

而不是让业务代码直接依赖所有具体算法类。功能未启用时，相关接口不存在或不可解析，能够尽早暴露配置错误。

服务端流程：

```text
接收 HTTPS 请求
  → 从路由或不可信索引取得唯一 Profile 候选
  → 校验协议版本、必要 Header 和时间窗口
  → 按 security_mode 验证 Token / 认证证明
  → 按 security_mode 验证最终 wire-level Body 的请求签名
  → 将密码学主体、client_id、issuer/audience、key 归属与 Profile 强制比对
  → ReplayStore 原子登记 Nonce（仅签名模式且已完成签名验证后）
  → 按需解密请求体并验证 AEAD
  → 校验 Scope
  → 执行业务
  → 序列化最终响应 Body
  → 按需加密响应，或按 Profile 生成响应完整性签名
  → 写入脱敏审计日志
```

若 `security_mode=token_only`，流程不登记请求 Nonce；该模式仅允许低风险、幂等路由。若 `security_mode=token_plus_request_signature`，Token 和签名必须都成功；任何一个失败均拒绝，绝不自动退化为另一个模式。

调用端流程：

```text
业务参数
  → 稳定序列化
  → 可选加密
  → 计算最终 Body Hash
  → 构造请求上下文
  → 按 security_mode 附加请求签名和/或 Token
  → 发送 HTTPS 请求
  → 验证响应完整性并可选解密响应
```

## 17. 协议版本和兼容性

SDK 版本与通信协议版本分开：

- SDK 版本使用语义化版本，如 `0.0.1`；
- 通信协议使用独立版本，如 `1`；
- 升级 SDK 不必升级协议；
- 一个 SDK 可在迁移期支持多个协议版本；
- 未支持协议必须明确拒绝，不能猜测或静默兼容。

`0.x` 阶段公共 API 可能调整，各项目固定明确版本；稳定后发布 `1.0.0` 并承诺兼容规则。

### 17.1 成熟期多语言总体路线

Laravel/PHP SDK 完成、测试稳定并进入成熟期后，将其作为首个成熟参考实现，逐步独立开发 Python、Go、Java、Android、HarmonyOS 和 iOS SDK。各语言 SDK 参考成熟包已经验证的功能边界、处理流程和安全规则，同时分别使用对应语言和平台的标准工程方式实现同一份语言无关协议。

这里的目标是扩大 Tozo Security SDK 家族的适用范围，不是让当前 Composer 包直接包含或运行其他语言代码。每种语言 SDK 都是独立软件包，拥有独立源码、依赖、测试、版本号和发布周期。

推荐采用“一个协议规范、多个独立 SDK”的结构：

```text
Tozo Security Protocol（唯一协议事实来源）
  ├── PHP/Laravel SDK（首个参考实现）
  ├── Python SDK
  ├── Go SDK
  ├── Java SDK
  ├── Android SDK
  ├── HarmonyOS SDK
  └── iOS SDK
```

协议规范与各语言 SDK 应独立版本化。某个 SDK 发布 `2.0.0` 不代表通信协议必须升级；兼容性依据是该 SDK 支持哪些协议版本。

### 17.2 语言无关协议制品

在启动第二种语言 SDK 之前，必须从 PHP 实现中提炼并冻结以下制品：

```text
protocol/
├── security-protocol-v1.md       请求、响应和处理顺序
├── profile-resolution-v1.md      Profile 候选、主体绑定与安全模式
├── canonicalization-v1.md        method/path/query/header/body 规范化
├── encryption-envelope-v1.json  加密信封 JSON Schema
├── token-profile-v1.md           Claims、kid、算法、吊销和验证规则
├── response-integrity-v1.md      响应加密/签名与方向绑定规则
├── error-codes-v1.json           对外错误码、内部原因码与映射
├── test-vectors/                 正常固定测试向量
├── negative-vectors/             篡改、过期、重放和错误密钥向量
└── compatibility-matrix.md       SDK 与协议版本兼容矩阵
```

协议必须明确字节级行为：UTF-8、换行符、空 Body、JSON 数字、Unicode、Query 排序、百分号编码、Header 大小写、Base64URL Padding、时间戳单位、Nonce 长度、AAD、方向字段和常量时间比较。还必须冻结 Profile 解析顺序、身份绑定断言、认证/签名组合、安全模式、ReplayStore 原子写入时点和 TTL、AES-GCM nonce 生成约束、JWT `kid` 轮换、Token 吊销失败策略和响应完整性规则。任何语言都不能使用本语言默认序列化结果代替协议规范。

### 17.3 各语言和平台的包形态

| 平台 | 建议实现与发布形态 | 能力定位 |
|---|---|---|
| PHP/Laravel | Composer 包 | 服务端完整能力和参考实现 |
| Python | Python 包，PyPI/私有索引 | 服务端完整能力及框架适配器 |
| Go | Go Module | 服务端完整能力及 `net/http` 中间件 |
| Java | Maven/Gradle 包 | 服务端完整能力，可扩展 Spring 适配器 |
| Android | Kotlin 优先、Java 可调用的 AAR/Maven 包 | 客户端认证、验签、Token 和安全存储 |
| HarmonyOS | ArkTS 包，通过 OHPM/HAR 分发 | 客户端认证、验签、Token 和安全存储 |
| iOS | Swift Package | 客户端认证、验签、Token、Keychain/Secure Enclave |

通用协议核心和框架适配器应分层。例如 Java 核心不应强制依赖 Spring，Python 核心不应强制依赖 Django/FastAPI，Go 核心不应强制绑定某个 Web 框架。

### 17.4 各语言版本的决定时点

当前提到的 Python 3.0、Go 1.25、Java JDK 20、Android、HarmonyOS 和 iOS 仅用于举例说明未来可能覆盖的语言或平台，不构成当前设计的最低版本、依赖约束或兼容承诺。

每个新语言 SDK 正式立项时，单独评估并冻结：

1. 当时仍受官方安全维护的语言和运行时版本；
2. 公司现有项目、合作方和终端设备的实际版本分布；
3. 所需密码库、HTTP 库和框架适配器的最低版本；
4. 对应生态的包管理和发布方式；
5. CI 能持续覆盖的最低版本、主流版本和最新稳定版本；
6. 版本停止支持策略和升级窗口；
7. 服务端完整能力或移动端受限能力的具体范围。

版本决定写入对应语言 SDK 自己的设计文档、包清单、README 和 CI 矩阵，不回填成当前 PHP/Laravel SDK 的运行约束。不同语言 SDK 可以采用完全不同的最低版本，也不要求版本号同步。

### 17.5 服务端与移动端能力边界

服务端 SDK 可以提供 Token 签发、合作方 HMAC、密钥轮换和持久化吊销。Android、HarmonyOS、iOS 属于不可信客户端环境，安装包可以被反编译，因此不能获得与服务端相同的能力：

- 不在移动端内置内部系统 HMAC 共享密钥；
- 不在移动端部署 JWT 签发私钥；
- 不允许移动端签发服务或合作方 Token；
- 移动端可以验证服务器公钥签名、管理用户 Token，并通过 Keychain/Keystore/Secure Enclave 保存设备私钥；
- 需要设备身份时，优先采用每台设备独立生成的非导出密钥和服务端注册公钥，不使用所有 App 共用的静态 secret；
- 移动端 Scope 只代表已登录用户或已注册设备权限，不能获得内部服务 Scope。

因此，各语言 SDK 共享协议核心，但不要求功能全集完全相同。每个 SDK 必须发布能力矩阵，明确 `supported`、`unsupported` 和 `server-only` 能力。

### 17.6 多语言发布准入条件

开始发布第二种语言 SDK 前，至少满足：

1. PHP/Laravel 参考实现已在真实调用链稳定运行；
2. 通信协议 v1 已冻结，SDK 版本与协议版本已分离；
3. 正常和负向测试向量已完成并通过安全评审；
4. 不依赖 PHP/Laravel 默认序列化行为；
5. 第二种独立语言实现与 PHP 实现双向互通；
6. 签名、加密、Token、Scope、错误码和密钥轮换均有一致性测试；
7. CI 对每种语言运行同一份协议测试向量；
8. 移动端 SDK 已完成密钥提取、重放和篡改威胁评审。

## 18. 异常、错误码和日志

异常建议：

```text
ConfigurationException
UnsupportedDriverException
AuthenticationException
SignatureVerificationException
ReplayDetectedException
EncryptionException
DecryptionException
TokenIssueException
TokenValidationException
ScopeDeniedException
KeyNotFoundException
ProtocolException
```

对外响应不得泄露密钥、签名原文、预期签名、Profile 名称、候选数量、密钥存在性或解密失败细节。对外错误码只表达可安全公开的类别；内部日志和审计使用更细的稳定原因码，两者必须通过 Protocol v1 的映射表关联。

对外错误码示例：

```text
invalid_signature
invalid_authentication
invalid_request
access_denied
temporarily_unavailable
```

内部原因码示例：

```text
token_expired
audience_mismatch
scope_denied
replay_detected
unknown_key_id
unsupported_protocol_version
profile_subject_mismatch
token_revoked
revocation_store_unavailable
replay_store_unavailable
invalid_security_configuration
```

日志可记录请求 ID、主体、客户端、Profile、协议版本、key ID、driver、目标接口、原因码和耗时。禁止记录密钥、私钥、完整 Token、Authorization Header、敏感 Body、解密明文、完整签名和 Refresh Token。

## 19. 安全默认值与失败原则

- 默认拒绝未知 Profile、driver、key ID 和协议版本；
- 对启用请求签名的 Profile 默认开启时间窗口和防重放；
- HMAC 使用常量时间比较；
- JWT 严格校验固定算法、签名、`kid`、issuer、audience、时间、主体、client 与 Scope；
- 新接入建议 HMAC-SHA256、AES-256-GCM、JWT-RS256；
- legacy driver 只能在明确标记为迁移中的 Profile 使用，并必须配置退役日期、责任人和目标替代协议；
- 配置、密钥、ReplayStore、TokenRevocationStore 或其他安全存储缺失时直接失败；
- ReplayStore 或吊销存储不可用时不绕过防重放或吊销检查；
- 加密、验签、Token 异常不被吞掉；
- `token_only` 不得用于写操作、资金、权限、敏感数据修改或外部合作方默认接入；
- 生产环境禁止输出安全中间值的调试接口。

## 20. 测试与验证

单元测试覆盖各 driver 的正常、篡改、错误密钥和边界条件；Profile 解析唯一性、Header/主体不一致、默认 Profile 入站拒绝；签名规范化固定向量；AES-GCM 的随机 96-bit nonce、nonce 外部注入拒绝、AAD/tag/密文篡改；Token `kid`、时间、issuer、audience、client、吊销和吊销存储故障；Scope 交集；用途密钥轮换；配置校验、显式 `null` 和日志脱敏。

集成测试覆盖 Laravel Middleware、调用端与服务端互通、`token_only` 路由限制、`token_plus_request_signature` 的 AND 条件、Redis 防重放原子性/多实例共享/TTL 下限、ReplayStore 故障 fail-closed、请求与响应的加密或签名完整性、固定 `response_integrity.mode` 对未受保护或模式不一致响应的拒绝、多 Profile 隔离、JWT `kid` 轮换、吊销 fail-closed、legacy 退役配置和 PHP/Laravel 支持矩阵。

首版最低版本以 Laravel `>=8.5` 和 PHP `>=7.4` 为基线。CI 必须以显式矩阵验证 PHP 7.4 与实际可运行的最低 Laravel 组合，以及每个计划在 Composer 约束中宣称支持的 Laravel 主版本与其所需 PHP 版本；不得宣称未经 CI 验证的未来 Laravel 主版本。PHP 7.4 已停止安全维护；保留它是为了兼容旧系统，新项目仍应优先使用受维护的 PHP 版本。

外部合作方和未来官方 SDK 可能不使用 PHP。协议文档必须提供固定时间戳、Nonce、Body、密钥、规范化字符串和预期签名/密文测试向量，供 Python、Go、Java、Android、HarmonyOS、iOS 及其他实现验证一致性。每个 SDK 的 CI 必须直接消费同一份只读向量，不能复制后各自修改。

## 21. 发布与分发方式

当前仅在本地目录讨论，正式仓库尚未确定。

### 21.1 个人 GitHub 私有仓库

可快速建立独立 SDK 仓库，Composer 通过 VCS 安装。必须确认公司代码政策、仓库私有性和访问权限，禁止提交业务密钥。启用分支保护、Tag 签名/受控发布、依赖审计和双因素认证；通过 HTTPS 访问仓库与 Composer 源。未来迁移到 GitLab 时应保持包名，并完成依赖来源、Tag 和发布工件校验。

### 21.2 内部 GitLab VCS

即使 Package Registry 未启用，也能让 Composer 从内部 Git 仓库安装，版本依赖 Git Tag；发布体验不如 Package Registry，但不阻塞 SDK 建设。正式生产分发必须使用 HTTPS 和受控证书，不能把 HTTP GitLab 地址当作安全 SDK 的长期供应链方案。

### 21.3 GitLab Composer Package Registry

Package Registry 是软件包制品库，负责按版本发布、安装、升级和回滚 SDK。它不是 API 网关、Token 签发中心或密钥管理系统。

```text
开发 SDK → 提交 Git → 创建 Tag → 发布 Package Registry → Composer 安装
```

当前内部 GitLab 检测信息（地址与版本号已脱敏，实际值见内部运维记录）：

```text
地址：http://<内部 GitLab 地址>/gitlab/
版本：14.x
/api/v4/user：正常
/api/v4/projects/{id}：正常
项目 packages_enabled：True
/api/v4/projects/{id}/packages：404 Not Found
```

该版本具备 Composer Package Registry 功能。`packages_enabled=True` 且项目 Packages API 返回 404 不能单独证明实例级功能未启用，还可能受反向代理路径、项目访问权限、许可证/功能开关或 API 路由配置影响。管理员应先在服务器侧检查实例配置、日志和同一认证主体权限，再决定是否启用：

```bash
sudo gitlab-rails runner 'puts Gitlab.config.packages.enabled'
```

Omnibus GitLab 配置：

```ruby
gitlab_rails['packages_enabled'] = true
```

应用配置：

```bash
sudo gitlab-ctl reconfigure
```

启用后，应以拥有项目访问权限的 Token 在正确的 GitLab 子路径下验证 Composer 端点与 Packages API；空项目通常返回空列表。该 GitLab 版本已停止安全维护，未来承载公司安全基础包前应安排升级。

## 22. 版本策略

```text
0.0.1  初始原型与基础协议
0.0.x  缺陷修复和小范围兼容调整
0.x.0  新模块或可能影响接入方式的变化
1.0.0  核心 API 和协议达到稳定承诺
```

业务系统通过 `composer.lock` 固定版本。升级 SDK 必须运行兼容测试，不能无审查地自动升级最新版。

成熟期各语言 SDK 使用各生态的语义化版本独立发布，并单独记录协议兼容范围，例如：

```text
PHP SDK 1.4.0       支持 Protocol v1
Python SDK 1.1.0    支持 Protocol v1
Go SDK 2.0.0        支持 Protocol v1、v2
Android SDK 1.0.0   支持 Protocol v1 客户端能力子集
```

不能使用“所有 SDK 版本号必须一致”替代兼容矩阵。

## 23. 渐进迁移方案

1. 盘点现有调用关系、算法、密钥来源和接口；
2. 建立核心接口、配置校验和一个推荐协议；
3. 选择风险低的一对 Laravel 系统试点；
4. 用 legacy adapter 接入一个旧协议验证兼容性；
5. 新接口只使用新协议；
6. 旧接口按调用链逐步迁移；
7. 每迁移一条链路，删除业务项目内对应的重复逻辑；
8. 完成密钥轮换、回滚和跨语言测试；
9. 再决定 GitHub、GitLab VCS 或 Package Registry。

迁移期允许新旧协议并行，但通过协议版本、路由或 Profile 明确区分，不能在验签失败后自动尝试其他算法。

## 24. 风险与控制

| 风险 | 控制措施 |
|---|---|
| 单包功能过多 | 内部模块化，首版控制功能范围 |
| SDK 缺陷影响多个系统 | 固定版本、测试、评审、分批升级 |
| 算法配置过于自由 | driver 白名单、启动校验、禁止请求动态选择 |
| 密钥继续散落 | 统一 KeyProvider，只从部署环境或受控文件读取 |
| Token 签发权扩散 | 签发默认关闭，私钥只部署至指定系统 |
| 时钟不一致 | NTP、有限 clock skew 和时钟监控 |
| ReplayStore 故障导致合法调用被拒绝 | 默认 fail-closed；部署共享高可用存储、监控连接与容量、容量隔离和限流；不使用自动 fail-open 降级 |
| Token 吊销存储故障导致已吊销 Token 逃逸 | 启用吊销即 fail-closed；独立监控 TTL、可用性和延迟 |
| Header 冒充 Profile 或客户端 | Header 只作候选索引；密码学主体与 Profile 强制绑定；候选不唯一直接拒绝 |
| AES-GCM nonce 重用 | SDK 内部 CSPRNG 生成 96-bit nonce；不开放外部 IV 注入；测试 nonce 唯一性与密钥用途隔离 |
| 响应被篡改或跨接口复用 | 响应使用 AEAD 或方向绑定的应用层签名；客户端先验证后交给业务 |
| 外部合作方不是 PHP | 独立协议文档和跨语言测试向量 |
| 多语言 SDK 产生协议漂移 | 单一协议仓库、共享测试向量、双向互通和兼容矩阵 |
| 移动端密钥被提取 | 不内置服务共享密钥或签发私钥，使用设备独立密钥和系统安全存储 |
| 旧算法长期存在 | 标记 legacy、统计使用量、制定退役时间 |
| 个人仓库存放公司安全代码 | 正式托管前确认公司政策、私有性、审计和所有权；启用分支保护、受控 Tag、HTTPS 和依赖审计 |

## 25. 首版验收标准

- 一个 Composer 包完成 Laravel 集成；
- PHP 最低版本明确为 `>=7.4`，Laravel 最低版本明确为 `>=8.5`；Composer 约束仅列出通过 CI 的 Laravel 主版本组合；
- SDK 不使用 MySQL，核心与首版不声明 MySQL 版本要求；
- 支持以通信信任关系为粒度的独立 Profile，且一个系统可拥有多个 Profile；
- 支持按应用实际使用情况按需注册功能模块，未启用功能不注册对应容器绑定；
- 认证、请求签名、加密、响应完整性和 Token 均通过白名单 driver 与显式安全模式配置；
- 服务端只把 Header 作为 Profile 候选索引，并验证密码学主体与 Profile 的强绑定；
- 支持 HMAC-SHA256 签名、时间戳、Nonce、共享 ReplayStore 原子写入和满足 TTL 下限的防重放；
- 支持 AES-256-GCM 请求/响应加解密，SDK 内部生成 96-bit CSPRNG nonce，禁止外部注入 IV；
- 支持响应 AEAD 完整性或独立用途的响应签名；
- 支持 JWT-RS256 的 `kid` 轮换和严格验证，签发默认关闭；
- 支持 `service`、`partner`、`user` 主体；
- 支持 Audience 和 Scope；
- 支持环境变量/文件 KeyProvider 和按用途区分的 key ID；
- 支持各用途密钥的有限迁移期与明确轮换规则；
- 启用 Token 吊销时，支持独立 TokenRevocationStore 且查询故障 fail-closed；
- 配置、密钥、ReplayStore、吊销存储或其他安全存储异常时明确失败；
- 日志不包含密钥、完整 Token 或明文敏感数据；
- 提供 Profile 解析、签名/加密/响应、Token/吊销和错误码的固定协议向量、单元测试和 Laravel 集成测试；
- 协议规范不依赖 PHP/Laravel 序列化行为，并能被其他语言独立实现；
- 覆盖 Profile → 应用默认值 → SDK 默认值的配置合并测试、显式 `null` 和安全必填参数缺失时的失败测试；
- legacy Profile 只在迁移期使用，且有退役日期、责任人和覆盖测试；
- 完成至少一条现有调用链路迁移验证。

## 26. 当前设计结论

当前推荐建设 `tozo/security-sdk` 单一 Composer/Laravel 包，以策略接口、Profile 和 KeyProvider 统一内部与外部 API 的身份、认证、签名、加密、Token 和 Scope。

算法可以配置，但配置权只属于部署方和服务端白名单，不能由请求方任意决定。Profile 隔离的是通信信任关系，而不是仅按系统命名。认证、请求完整性、加密和授权必须按显式安全模式组合；Token 验证不等于当前 HTTP 请求已防篡改。Token 签发默认关闭，只部署到明确授权的签发系统。

当前先保留在本地目录讨论。个人 GitHub 私有仓库、内部 GitLab VCS 和 GitLab Package Registry 都是后续可选发布方式，不影响核心包名和架构。

PHP/Laravel SDK 成熟后，以其验证过的逻辑作为参考，以语言无关协议、共享测试向量和兼容矩阵作为一致性标准，分别独立建设 Python、Go、Java、Android、HarmonyOS 和 iOS SDK，从而扩大整个 SDK 家族的使用范围。各语言具体版本在对应 SDK 实际立项时决定。服务端 SDK 可提供完整能力，移动端 SDK 只提供经过安全限制的客户端能力子集。

## 27. 进入实施前需冻结的决策

1. 正式中文名称、Composer 包名和 PHP 命名空间；
2. PHP `>=7.4`、Laravel `>=8.5` 的支持矩阵，以及每次发布实际写入 Composer 的已验证 Laravel 主版本；
3. 首版必须实现的 driver 列表，以及 `jwt_hs256`、`opaque_token`、Refresh Token 是否延期；
4. Profile 最终配置结构、信任关系粒度、入站/出站角色、Profile 解析顺序和主体绑定断言；
5. `token_only` 的允许路由清单，以及 `token_plus_request_signature`、`signed_request` 的强制适用范围；
6. 请求/响应规范化、Header、Nonce、ReplayStore 原子语义和 TTL、加密信封、AES-GCM nonce 与 AAD 的精确字节协议；
7. 响应完整性模式、用途密钥分离、密钥轮换窗口和 legacy Profile 退役机制；
8. Token 签发系统、私钥部署边界、JWT `kid` 公钥分发和 TokenRevocationStore 的可用性目标；
9. 第一对试点系统、路由风险分类及旧协议迁移/回滚方式；
10. 正式代码托管位置、HTTPS/Tag/发布工件供应链控制和发布渠道；
11. 协议规范与 SDK 代码的仓库边界、测试向量所有权和错误码映射；
12. 多语言阶段各平台受维护版本、包管理器和能力矩阵。
