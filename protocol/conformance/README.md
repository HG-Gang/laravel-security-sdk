# 跨语言一致性验证

本目录存放**独立于 PHP SDK** 的 Protocol v1 参考实现，用途只有一个：证明协议规范真正语言无关。

## 为什么需要

`protocol/test-vectors-v1.json` 由 PHP 实现生成。如果只有 PHP 消费它，就是"实现自证实现"——向量对协议没有约束力。只有当**从零编写、不移植 PHP 源码**的其他语言实现也能逐字节复现，才能说明规范本身是完备且无歧义的。

这里的实现刻意避开各语言的"便利函数"：

| 语言 | 刻意不使用 | 原因 |
|---|---|---|
| Python | `urllib.parse.parse_qs` | 会把重复键折叠成列表并丢失原始顺序 |
| Python | `quote` 默认 safe 集 | 默认保留 `/`，与协议要求的未保留字符集不符 |
| Go | `net/url.ParseQuery` | 返回 map，丢失重复键顺序，方括号键被当作字面键名 |
| Go | `url.QueryEscape` | 把空格编码为 `+`，协议要求 `%20` |
| Go | `map[string]interface{}` | 遍历顺序随机，无法复现 wire 字节 |

## 运行

```bash
# Python（仅标准库，3.7+）
python protocol/conformance/python/conformance_test.py

# Go（仅标准库，1.21+）
cd protocol/conformance/go && go run .
```

两者都在成功时输出比对项数与"逐字节一致"，返回码 `0`；不一致时逐条打印 expected/actual 并返回 `1`。

也可用统一入口一次跑完 PHP + Python + Go：

```bash
composer run conformance
```

## 出现不一致时怎么办

**先判断性质，再决定改哪边。** 两种情况处理方式相反：

1. **该语言实现理解偏差** —— 改实现。典型表现：只有一种语言不一致，且该语言的偏差能追溯到某个便利函数的隐含行为。
2. **协议规范有歧义** —— 改 `protocol/README.md` 把规则写清，必要时升协议版本。典型表现：两种以上语言给出相同的"另一种"结果，说明规范的文字表述允许多种合理解读。

**任何情况下都不要为了让测试通过而修改向量的 `expected` 值。** 向量是契约。

## 已经通过本机制发现的规范缺陷

### 空 query 的 JSON 表示（2026-08-27）

初版向量中 `canonical_query_array[].input` 的空值写作 `[]`。PHP 的 `json_decode('[]', true)` 得到空数组，与空映射同型，测试通过；但 Python 读到的是 `list`，Go 读到的是 JSON 数组——都不是映射，直接抛类型错误。

这是 PHP 数组不区分列表与映射的语义泄漏到了协议制品里。修复：生成器对该字段强制 `(object)` 转换，空 query 序列化为 `{}`。

这条缺陷单靠 PHP 测试永远发现不了——正是跨语言验证的价值所在。

## 新增语言实现

1. 在本目录下新建 `<语言>/` 子目录。
2. 按 `protocol/README.md` 的**文字规则**实现，不要读 PHP 源码。
3. 消费 `protocol/test-vectors-v1.json`，覆盖全部 10 个向量组。
4. 成功输出比对项数，返回码 `0`；失败逐条打印并返回 `1`。
5. 在 `.github/workflows/ci.yml` 的 `protocol` 作业中加入执行步骤。
6. 更新本文件的「当前状态」表。

实现完成后，若发现任何与向量不一致之处，按上一节判断性质后处理。

## 范围说明

这些实现**只覆盖协议的纯函数部分**：规范化、编码、签名原文构造、HMAC 计算。

不覆盖也不打算覆盖：HTTP 传输、Profile 配置解析、密钥管理、ReplayStore、Token 签发验证、中间件。那些属于各语言 SDK 的职责，不是协议一致性的验证对象。

因此这里的实现**不是可用的 SDK**，不要在生产中引用。
